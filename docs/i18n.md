# Languages

CargoFrame speaks English, French, Spanish, Italian and German (0.6.0). English is written in the code; each
other language is a **pack** that maps the English text to its translation. A pack is a plain JSON file, so it can
be read and corrected by anyone, and a missing text simply shows in English.

| Packs | For |
|---|---|
| `ui/src/lib/i18n/packs/<code>.json` | Settings and the CargoFrame window (Svelte) |
| `core/i18n/packs/<code>.json` | What the program itself says: connector texts and errors, checks, templates, the tray menu, notifications, the items of the System page (Rust) |

The language follows the computer by default; **Settings › Preferences › Language** can choose one. Changing it opens
Settings again in the new language, the tray menu changes at once, and windows kept ready are let go so the next
capture opens in the new language. A CargoFrame window already on screen keeps its language until it closes, so
nothing typed in it is lost.

## What is translated, and what is not

- Every label, hint, message, error and guide the person reads, and the default names of what CargoFrame makes for
  them (a new block's title, a template's blocks, a new trigger's example name).
- **Not translated:** what the person typed or chose (layout names, block titles, starting texts once saved), the
  names of services and products, and the names of buttons on other sites that the help texts tell the person to
  press (*Create New App*, *Copy Link*, *Generate token*): those sites are often in English, and the person looks
  for the words they see. Technical strings stay as they are: queries sent to a service (JQL, Drive queries), header
  values, command lines, `{names}` and the syntax of data rules (`line:`, `tail:`, `name`, `size`).
- Low-level details from libraries (a TLS or file-system error) are shown as they come, inside a translated sentence.

## Writing a text in the code

**Svelte and TypeScript** (`ui/src/lib/i18n/index.svelte.ts`):

```ts
t('Save locally')                              // the text in the language in use
t('Signed in as {name}', { name })             // {names} are filled in after translating
tn('{n} file', '{n} files', count)             // one or several
msg('Layouts')                                 // only marks a text kept in data; t() it where it is shown
```

`<Tr text={t('Press {key} to…')}>` draws a sentence with a marked-up part (a snippet per `{name}`).

**Rust** (`core/i18n`):

```rust
t("Not found")                                 // &'static str in the language in use
tf("Posted to r/{sub}", &[("sub", &sub)])      // filled in after translating
msg!("Shortcut to capture ready")              // a const or a table: translate with t() where it is shown
```

Rules that keep translations correct:

- **Write whole sentences.** Never build a sentence from pieces (`"your " + what`, `"file" + "s"`): French, Spanish,
  Italian and German change word order, gender and case. Two sentences, or `tn`, cost nothing.
- **Name the values** (`{size}`, `{max}`), never `{}` or `{value2}`: the translator needs to know what goes there.
- A text that ends up inside another (a `{what}` for "Could not {what}") is a phrase the bigger sentence was written
  for. Keep such phrases few; the glossary below says how each language writes them.
- Don't lowercase or capitalize a translated text in code: German nouns keep their capital.

## Each push: packs stay in step

`node scripts/i18n/check.mjs` reads every `t`/`tn`/`msg` call in `ui/src` (both texts of a `tn`, its plural also when
written `t('…')`: 0.7.2) and every `t`/`tf`/`msg!` call in the Rust crates (a `t(` split over lines by rustfmt, with its trailing comma, too: 0.7.2), and fails when a pack is missing a text, still has one the code no longer has, or translates a text with
other `{names}`. It runs in `scripts/dev/check.sh` and in CI, so **a change that adds or changes a text adds its
translations in the same pull request.** A text passed to `t()` through a variable (a table of labels) is marked
`msg!("…")` where it is written, so the check finds it.

```sh
node scripts/i18n/check.mjs                 # what is missing or stale, per pack
node scripts/i18n/check.mjs --missing > todo.json   # {area: {lang: {english: ""}}} to fill in
node scripts/i18n/check.mjs --merge todo.json       # add the filled-in translations to the packs
node scripts/i18n/check.mjs --prune         # drop texts the code no longer has
node scripts/i18n/check.mjs --where         # every text and a file it is in, to see where it is shown
```

When translating, open the file `--where` names and look at what the control does: the translation says what the
button or message means there, not word for word. A text used in two places must fit both.

## Adding a language

1. Add its code and its own name to `LANGUAGES` in `core/i18n/src/lib.rs` and `ui/src/lib/i18n/index.svelte.ts`,
   and its pack to `PACKS`.
2. Create both packs as `{}` and fill them with `--missing` and `--merge`.
3. Look at Settings and a capture window in it (`localStorage['cargoframe.demo.language']` in the browser preview).

## Glossary

Register: French *vous*, Spanish *tú*, Italian *tu*, German *Sie*. The words are the ones current technical tools use
(*raccourci*, *log*, *cattura*), not the textbook ones (*déclencheur*, *journal*, *acquisizione*); English loan words
that people in the field say (*log*, *layout*, *zip*, *token*) stay as they are.

**Action phrases** (the `{what}` of "Could not {what}", "Jira answered {what} with something unreadable"): French,
Spanish and Italian use the infinitive (*publier sur Bluesky*, *publicar en Bluesky*, *pubblicare su Bluesky*);
German uses the *zu*-infinitive (*auf Bluesky zu posten*) after *Es war nicht möglich,*.
